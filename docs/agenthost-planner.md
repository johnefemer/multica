## TL;DR

A chat page at `/build-your-team` interviews a visitor about their project, drafts a tailored AI development plan, and emails them (and up to 3 teammates) a private hotlink to the full plan. The chat IS the form — there's no separate `<input>` for name / email. The page is the marketing site's primary lead magnet: every completed conversation = a `planning_lead` row + a Resend email + qualified context for sales.

```
visitor → /build-your-team → 6-question interview → generate_plan tool
                                                           │
                                                           ▼
                          conversational email collection (name, email, cc)
                                                           │
                                                           ▼
                           submit_capture tool → planning_lead row + Resend
                                                           │
                                                           ▼
                                          /plan/<hash>  (private hotlink)
```

## Goal — why this exists

### As a lead magnet

The marketing site has three pricing tiers (Solo / Team / Frontier) and a `/10x` programme page. None of them solve the founder's actual question: *"which one fits me, and what does it look like to actually use Agenthost on my project?"*

The planner answers both, and in doing so:

| Lead-magnet property | How the planner does it |
|---|---|
| **Capture qualified intent** | A user willing to spend 5 minutes describing their project is a much stronger lead than one who clicks "Contact us" |
| **Capture qualitative context** | Sales gets the full conversation transcript, not just an email + form fields. They know the stack, stage, team shape, and current pain before the first reply |
| **Demonstrate the product** | Agenthost is an agent platform; using a real Anthropic agent on the marketing site is the most honest possible product demo |
| **Recommend a tier** | The agent picks one of `solo` / `team` / `frontier` and explains why — visitors stop bouncing on the pricing page because "they're not sure" |
| **Email gives sales a permanent surface** | The plan email is read in the inbox days later. Replies thread back to `agenthost@kensink.com` for human follow-up |

### The value exchange

The user gets a tailored plan; we get an email + transcript. The plan is real (not a generic template) — that's the deal. If the plan is generic, the trade falls apart and the visitor knows it.

This is why:
- The plan is generated by Opus 4.7 with the user's actual stack and stage in context, not a template engine.
- The system prompt forbids marketing speak (*"leverage", "synergy", "best-in-class", "harness the power of"*).
- The email body shows a real plan summary, not a "thanks for your interest" note.

### What it isn't

The planner is **not**:

- A general-purpose chatbot (the system prompt redirects off-topic questions exactly once, then again, and stays on the planning track)
- A replacement for sales calls (the bottom CTA on `/build-your-team` and on `/plan/<hash>` both lead to `mailto:agenthost@kensink.com`)
- A signup flow (the email is for plan delivery, not account creation; nothing is provisioned in the product)
- A free tech-advice service (off-topic technical questions are politely declined)

## User journey

### 1. Discovery

The visitor lands on `/build-your-team` from one of:

- **Header nav** — `// PLAN` with a `BETA` badge, sits between `WORKFLOW` and `PRICING` ([ops-header.tsx](../apps/web/features/landing/components/ops/ops-header.tsx))
- **Direct link** — anything we put in social posts, sales replies, or onboarding emails
- **(Future)** — pricing page CTA, homepage hero, footer Resources group (deferred)

### 2. Hero + first message

The page renders inline: a hero ("PLAN YOUR AI TEAM. IN 5 MINUTES."), a how-it-works card, a metadata strip (~6 questions / architecture + roadmap / solo–team–frontier / email + private link / ~5 minutes), and the chat panel with one seeded greeting:

> *Hey 👋 I'm the Agenthost planner. In ~5 minutes I'll map an AI dev team for your project — architecture, CI/CD, roadmap, and the right tier. To start: what are you building? One paragraph in your own words is enough.*

### 3. Focus mode

The moment the user sends their first message, the chat panel becomes a fixed full-viewport overlay with a backdrop. The marketing page underneath stops scrolling. On mobile this goes edge-to-edge with `100dvh` so the keyboard reflows correctly.

### 4. Six-question interview

The agent asks **one question per turn**. Targets six facts:

1. **What** they're building (free-form paragraph)
2. **Stage** — idea / pre-MVP / live with users / scaling
3. **Team shape** — solo / 2–3 / 4–10 / 10+; engineers vs PM/design split
4. **Stack** — main language, deploy target, repo count
5. **CI/CD posture** — none / GitHub Actions / mature pipeline
6. **Current pain** — one sentence on what's blocking them

The system prompt allows the agent to skip facts already given in earlier answers, drill into ambiguity with one short follow-up, and refuse off-topic questions ("explain SOLID", "what's a vector database", etc.).

### 5. Plan generation

When the agent has enough signal (typically 5–7 user turns), it calls the `generate_plan` tool **without preamble** ("Let me put your plan together…" is explicitly forbidden in the system prompt — just call it).

The tool input is a strict JSON schema with five required fields:

| Field | Shape |
|---|---|
| `recommended_tier` | enum: `solo` / `team` / `frontier` (defaults to `team` unless clearly solo or enterprise) |
| `tier_why` | one sentence under 120 chars explaining the fit |
| `plan_summary` | exactly two sentences — first describes the project, second is the plan headline |
| `gist_bullets` | 4–5 specific bullets pulled from the plan, each under 100 chars |
| `plan_markdown` | the full plan in Markdown, ~600–900 words, six sections |

Server-side, this triggers a `plan_ready` stream event. The client stores the plan in state.

### 6. Conversational email collection

After `generate_plan`, the agent **continues the chat** to collect the email. It does **not** end the conversation. The system prompt prescribes:

> *7. Acknowledge + ask for name. One short sentence confirming the plan is ready (mention the recommended tier in passing if natural), then ask for their name.*
>
> *8. Ask for email.*
>
> *9. Ask for teammates. "Want to share with teammates? Drop up to 3 emails (comma-separated), or say 'just me'."*

`skip` / `just me` / `no` / `not now` / `solo` all map to an empty `cc_emails` array.

### 7. Capture

Once name + email are collected and teammates list (or empty) is known, the agent calls `submit_capture(primary_name, primary_email, cc_emails)`. The route handler:

1. Validates the LLM-supplied input (defensive — strict tool schema is the primary guard)
2. Generates a 10-char base62 hash via `crypto.randomBytes(10)` mapped to alphabet `[0-9A-Za-z]`
3. Inserts a `planning_lead` row with retry-on-collision (`23505`)
4. Renders a Resend email per recipient (HTML + plain-text fallback) with the inline plan summary, gist highlights, recommended-tier callout, and the hotlink CTA
5. Streams `capture_started` then `capture_completed` events to the client
6. Returns a tool_result to the LLM with the hash + `plan_url`, instructing it to confirm delivery

### 8. Confirmation

The agent's final chat turn includes the hotlink inline:

> *Sent — check mei@studio.com. Your private plan link: https://agenthost.pro/plan/abc123def0*

### 9. Reading the full plan

Recipients receive an email with the plan summary + a `Open your full plan →` button pointing at `/plan/<hash>`. The page is server-rendered, neon-accented (`#39ff88`), `noindex,nofollow`, and disallowed in `robots.txt`. There's no auth — the hash itself is the credential, and the keyspace is large enough (~60 bits) to make brute-force enumeration impractical.

The plan page shows:

- Hero: `// PLAN_FOR_<NAME>` eyebrow, headline, project summary
- Tier card with the recommended tier + a `SEE_PRICING_DETAIL →` link
- Metadata strip (plan owner, created date, version, plan ID)
- The full plan markdown in a 800px reading column
- A `// QUESTIONS · READY TO DEPLOY?` reply CTA at the bottom

### 10. Sales hand-off

The recipient can:

- Reply to the email → inbox at `agenthost@kensink.com`
- Click `EMAIL_AGENTHOST →` on the plan page → opens `mailto:` with the plan ID + name in the subject
- Click `SEE_PRICING_DETAIL →` → goes to `/pricing#<tier>` (anchor on the recommended tier)

## Architecture

```
┌────────────────────────────────────────────────────────────────────┐
│  Browser                                                            │
│  apps/web/features/landing/components/build-your-team-page-client  │
│    state: messages, phase, plan, capture                            │
│    NDJSON stream parser (delta / plan_ready / capture_*  events)    │
└────────────────────────┬───────────────────────────────────────────┘
                         │ POST /api/landing/team-planner/chat
                         │ (full message history each request — stateless)
                         ▼
┌────────────────────────────────────────────────────────────────────┐
│  Next.js route handler   apps/web/app/api/landing/team-planner/    │
│  Multi-turn agentic loop within one HTTP request:                   │
│    while (i < 5):                                                   │
│      stream = client.messages.stream({...tools, messages})          │
│      forward text deltas → client                                   │
│      finalMessage = await stream.finalMessage()                     │
│      if end_turn: break                                             │
│      if tool_use:                                                   │
│        for each tool:                                               │
│          generate_plan → emit plan_ready, store, tool_result        │
│          submit_capture → executeCapture(), emit capture_*,         │
│                           tool_result with hash + plan_url          │
│      messagesForApi.push(tool_results)                              │
│      loop                                                           │
└────────────────────────┬───────────────────────────────────────────┘
                         │
        ┌────────────────┴────────────────┐
        ▼                                  ▼
┌──────────────────────┐         ┌──────────────────────────────┐
│  Anthropic API       │         │  Postgres (capture-service)  │
│  Opus 4.7 + adaptive │         │  INSERT planning_lead RETURNING│
│  thinking            │         │  id, hash                     │
│  Cached system prompt│         └──────────┬───────────────────┘
│  Tools:              │                    │
│    generate_plan     │                    ▼
│    submit_capture    │         ┌──────────────────────────────┐
└──────────────────────┘         │  Resend                      │
                                 │  send 1..N emails            │
                                 │  (primary + cc_emails)       │
                                 └──────────────────────────────┘

       /plan/<hash>  (server-rendered, noindex, robots disallow)
                       │
                       └──→ getLeadByHash() → render plan_markdown via
                            react-markdown with custom component overrides
```

### Data flow per user message

```
User types → POST /api/landing/team-planner/chat with full history (text-only)
   │
   ├─ Server validates body (alternating roles, length caps, MAX_TURNS=30)
   ├─ Server starts Anthropic stream call #1
   │     Tools: [generate_plan, submit_capture]
   │     System prompt: cached (4096+ tokens, ephemeral cache_control)
   │     Adaptive thinking: enabled
   │
   ├─ Stream events arrive:
   │     content_block_delta(text_delta)  → forward as `{type: "delta"}`
   │     content_block_start(tool_use)    → forward as `{type: "tool_call_started"}`
   │
   ├─ finalMessage().stop_reason
   │     end_turn   → done, close stream
   │     tool_use   → resolve tool(s), append tool_result, loop
   │
   └─ done → close NDJSON stream
```

## Key design decisions

### Why Next.js (not Cloudflare Agents or Firebase Genkit)

We considered both. Cloudflare Agents (Durable Objects + Workers AI) and Firebase Genkit are frameworks for stateful, long-running agent runtimes. The planner needs **none** of that:

- One conversation per visitor, ≤10 minutes
- ≤5 LLM calls total
- One transactional email batch at the end
- One DB row inserted

The cost of either framework is a second deployment target, second auth surface, second incident channel. The Anthropic API key was already on the box for the Go backend's email use case. Postgres + Resend already wired up. Adding a Next.js route handler is the path of least resistance — and means the same `kensink-v2` push that ships marketing copy ships planner changes too.

### Why the chat is the form

Originally there was a separate `EMAIL_THE_PLAN` section below the chat with `<input>` fields for name, email, teammates. Two problems:

1. Visually disjoint — felt like a "thanks for chatting, now please fill out this form" bolt-on
2. Gave away the trick — the chat felt like marketing material once a real form appeared

Moving the email collection into the chat itself (as a continuation of the same agent conversation, gated by a second tool) made the page feel like one cohesive experience. The agent extracting `name + email` from a single user reply ("I'm Mei, mei@studio.com") feels more natural than tabbing through three labelled inputs.

### Why Opus 4.7 and not Haiku 4.5

The skill rule is "never downgrade for cost — that's the user's decision." Beyond that:

- The plan markdown is the value exchange. Generic plans kill the whole funnel.
- Opus 4.7's adaptive thinking handles the off-topic guard and tier-recommendation reasoning much better than Haiku.
- Even at ~$5/1M input + $25/1M output, the cost per completed conversation is small (~$0.05–0.20) compared to a sales-qualified lead's value.
- Prompt caching cuts the input cost by ~10× on warm caches; the system prompt is intentionally padded above the 4096-token cache minimum.

### Why two tools (`generate_plan` + `submit_capture`)

Instead of one mega-tool that takes everything, we split:

- `generate_plan` — runs once when the interview is "enough"; returns the plan structure
- `submit_capture` — runs once after name/email are collected; sends the emails

Splitting forces the agent to **show the plan first**, which:

1. Lets the page UI react to `plan_ready` (show the gist preview, switch indicator label to `// SENDING THE EMAIL`)
2. Means the user sees a tier recommendation before being asked for an email — the value is delivered first
3. Lets `submit_capture` fail (Resend down, bad email) without losing the plan data

The system prompt enforces: never call `submit_capture` before `generate_plan`; never call either twice; never call `submit_capture` without a name AND email.

### Why a server-side agentic loop in one HTTP request

The naive design would have the client orchestrate: send a message → if response includes a tool call, the client resolves it and sends another request. That works but:

- Triples the round-trip latency
- Requires the client to know about every tool's semantics
- Means tool results live in client state (more surface for tampering)

Doing the loop server-side keeps the client dumb (it just receives a stream of `delta` events plus a few special signals) and keeps tool resolution where the credentials live (the Anthropic key, the DB connection, the Resend key are all server-side).

### Why a 10-char base62 hash

The user asked for "short" hashes. Tradeoffs:

| Length | Keyspace | Brute-force at 1 req/sec |
|---|---|---|
| 8 chars | 218 trillion | ~7M years |
| 10 chars | 8.4 × 10¹⁷ | well past heat death |
| 32 chars | infeasible | overkill, also ugly |

10 was a comfortable middle ground — share-friendly, easy to read aloud, unguessable without rate limiting (which PR 5 will add as defense in depth).

### Why a self-contained plan page (neon accent, no tokens.css)

The plan hotlink is a **standalone reading experience**. Earlier versions wrapped the page in `OpsPageShell` which dragged in `tokens.css`, the i18n provider, and the marketing header/footer. Result: the hotlink felt like a marketing page, the locale provider crashed because the route lived outside `(landing)`, and content lines overlapped because of layout interactions.

Rewriting the plan page with **zero external CSS bindings** (just Tailwind + a single `PLAN_ACCENT` constant) gave the page:

- A clean, focused B&W aesthetic with one neon accent (`#39ff88`)
- No locale dependency, no overlap quirks, no scroll-lock side effects from focus mode
- Visual identity distinct from the marketing site — feels like a "plan dossier", not a landing page

### Why robots disallow + page-level `noindex`

Both. The page-level `noindex,nofollow` metadata tells well-behaved crawlers to skip indexing. The robots.txt `Disallow: /plan/` tells them not to fetch in the first place. Belt and braces — neither alone is sufficient against poorly-behaved crawlers, and the cost of both is one line each.

## Configuration

### Environment variables

All set in `/opt/multica/.env` on the agenthost EC2 box. The compose file passes them through to the `agenthost-frontend-1` container.

| Variable | Required | Notes |
|---|---|---|
| `ANTHROPIC_API_KEY` | yes | Server-side only. Never reaches the browser. Without it, `/api/landing/team-planner/chat` returns 503. |
| `DATABASE_URL` | yes | Same Postgres as the Go backend. The chat container needs its own connection pool (`pg`, max 5 — see `lib/db.ts`) |
| `RESEND_API_KEY` | yes | Same key the Go backend uses for verification emails. If unset, the lead is still saved but no emails go out (logged as a warning). |
| `RESEND_FROM_EMAIL` | optional | Defaults to `Agenthost <noreply@kensink.com>` |
| `AGENTHOST_APP_URL` | recommended | Used to build absolute hotlink URLs. Defaults to `https://agenthost.pro` |
| `MULTICA_APP_URL` | legacy | Same as above; both are checked, AGENTHOST_APP_URL wins |

### Schema migration

`server/migrations/066_planning_lead.up.sql` — auto-applies on backend container start (entrypoint runs `./migrate up` before starting the server). The chat code does not run migrations; it just expects the table to exist.

To verify on prod:

```bash
ssh -i ~/.ssh/agenthost.pem ubuntu@54.82.211.103 \
  "docker exec agenthost-postgres-1 psql -U multica -d multica \
     -c \"SELECT version FROM schema_migrations WHERE version LIKE '066%';\""
```

### Nginx routing

`/api/landing/*` is the **only** `/api/*` prefix that does not route to the Go backend. The location block must be listed before the generic `/api/` block in `scripts/nginx/agenthost.conf` (nginx prefix-match wins by ORDER, not specificity, when both match):

```nginx
location /api/landing/ {
    proxy_pass         http://multica_frontend;
    proxy_buffering    off;        # NDJSON streaming
    proxy_read_timeout 300s;       # interview can take ~3 min
    ...
}

location /api/ {
    proxy_pass http://multica_backend;
    ...
}
```

Manual deploy step: nginx config changes don't ship via the GHA pipeline. After committing changes to `scripts/nginx/agenthost.conf`, ssh and:

```bash
sudo cp /opt/multica/scripts/nginx/agenthost.conf /etc/nginx/sites-available/multica
sudo nginx -t && sudo systemctl reload nginx
```

## Operations

### Querying leads

```bash
# Recent leads with conversation length
ssh -i ~/.ssh/agenthost.pem ubuntu@54.82.211.103 \
  "docker exec agenthost-postgres-1 psql -U multica -d multica -c \"
    SELECT
      hash,
      primary_email,
      primary_name,
      recommended_tier,
      array_length(cc_emails, 1) AS teammate_count,
      jsonb_array_length(conversation) AS turns,
      length(plan_markdown) AS plan_chars,
      created_at
    FROM planning_lead
    ORDER BY created_at DESC
    LIMIT 20;
  \""

# Conversion funnel (count by recommended tier)
ssh -i ~/.ssh/agenthost.pem ubuntu@54.82.211.103 \
  "docker exec agenthost-postgres-1 psql -U multica -d multica -c \"
    SELECT recommended_tier, COUNT(*) AS leads
    FROM planning_lead
    GROUP BY recommended_tier
    ORDER BY leads DESC;
  \""

# Read one conversation (for support / sales prep)
ssh -i ~/.ssh/agenthost.pem ubuntu@54.82.211.103 \
  "docker exec agenthost-postgres-1 psql -U multica -d multica -c \"
    SELECT jsonb_pretty(conversation) FROM planning_lead WHERE hash = 'abc123def0';
  \""
```

### Common failure modes

| Symptom | Likely cause | Fix |
|---|---|---|
| Page loads but chat 404s in prod | nginx config not redeployed after a `scripts/nginx/agenthost.conf` change | SSH + cp + nginx -t + systemctl reload |
| Chat returns 503 with `planner not configured` | `ANTHROPIC_API_KEY` missing or empty in `/opt/multica/.env` | Add the key, force-recreate frontend container |
| Plan email never arrives | `RESEND_API_KEY` unset OR domain not verified in Resend | Check `docker logs agenthost-frontend-1` for `RESEND_API_KEY not set` warning OR `[capture-service] resend failed for ...` |
| `/plan/<hash>` shows "page couldn't load" | A LocaleProvider crash on the plan page. Should not recur — plan-page-shell is now self-contained and doesn't use `useLocale`. | If it does, check `docker logs agenthost-frontend-1` for `useLocale` errors |
| Hotlink in email goes to a 404 | The lead row was deleted, OR the hash in the email is malformed | `SELECT hash FROM planning_lead WHERE hash = '<hash>'` — if missing, the row is gone; otherwise check for whitespace/typo |
| Agent talks about Agenthost features that don't exist | System prompt drift — usually means a recent edit to `system-prompt.ts` softened the "do not invent features" rule | Review the prompt's "core capabilities" list and the hard rules section |
| Agent gets stuck in the interview after >10 turns | The agent is waiting for a fact it never gets, OR the user is being terse. Currently no escape hatch — `MAX_TURNS = 30` will eventually 400. | Future: add a "give up gracefully and call generate_plan with what we have" instruction in the prompt |

## When you change the system prompt

The prompt is the load-bearing piece of this whole feature. Editing it without testing is dangerous. After any change to [`system-prompt.ts`](../apps/web/lib/landing/team-planner/system-prompt.ts):

1. Run a real interview locally (`pnpm dev:web`, `ANTHROPIC_API_KEY=...` in `apps/web/.env.local`).
2. Try at least one off-topic question mid-interview ("explain SOLID", "what's a vector database") — the agent should redirect once and continue.
3. Test all three tier paths — describe a clearly solo project, a 5-person team, and a 50-person enterprise. Confirm the tier picks track.
4. Test the email collection flow — confirm the agent doesn't re-ask for facts it already has, doesn't call `submit_capture` without a name+email, doesn't send a long monologue after delivery.
5. Check the prompt is still > 4096 tokens (run `client.messages.count_tokens(...)` against the rendered system prompt) — if it dropped below, prompt caching silently stops working.

The prompt's "Padding (for prompt cache)" section at the bottom is intentionally there to clear the cache minimum. Don't trim it without re-checking the token count.
